# 파레토 최적화 게이트 (Pareto Optimization Gate)

두 지표가 서로 밀당하는 산출물을 개선할 때, **한 지표만 보고 판정하면 반드시 속는다.** 이 스킬은 개선 시도를 파레토 곡선 위에 놓고 "진짜 개선인지 트레이드오프인지"를 기계적으로 가른다.

출처: 운영자 스킬 라우팅 벤치 실측(2026-07-24, 6라운드) — 프롬프트로 R을 0.58→0.81까지 올렸으나 P가 0.56→0.33으로 붕괴, F1은 오히려 하락한 실패에서 확립.

## 언제 쓰나 (트리거 도메인)

상충 지표쌍이 있는 모든 개선 작업:
- **라우팅/분류**: recall(맞는 걸 집나) ↔ precision(불필요한 걸 안 집나)
- **리트리벌/검색**: 재현율 ↔ 정확도
- **감사(audit)·이상탐지**: 민감도(sensitivity, 놓치지 않기) ↔ 특이도(specificity, 오탐 안 내기). 감사 임계값을 조이면 오탐↓지만 적발누락↑ — 정확히 파레토 문제.
- **evaluator/게이트**: 통과율 ↔ 오통과 방지
- **AKM/지식관리 점수**: 커버리지 ↔ 신호밀도

## 핵심 개념 3개

### 1. 지표는 눈금, 레버는 손잡이 (혼동 금지)
- **R·P·F1·민감도·특이도 = 결과를 재는 자(지표).** 목표가 아니라 온도계. "R을 올린다"는 "R 손잡이를 돌린다"가 아니라 "레버를 돌려 R 눈금이 오르게 한다".
- **레버 = 실제로 바꾸는 것**: 프롬프트, 데이터(desc·규칙·코퍼스), 임계값(threshold), 루프(다수결 등).
- 🔴 레버를 지표로 착각하면 "R이 안 오른다 → R을 더 세게"처럼 헛돈다. 항상 "어느 레버를 돌려 어느 지표가 움직였나"로 서술.

### 2. 다이얼 레버 vs 곡선 레버 (가장 중요)
- **다이얼 레버 = 곡선 *위*를 좌우 이동.** 한 지표 올리면 다른 게 내려간다. 예: 프롬프트("널널하게 골라라"↔"짜게 골라라"), 분류 threshold, 감사 컷오프. **F1(조화평균)은 거의 안 변한다** — 파레토 프론티어 위를 미끄러질 뿐.
- **곡선 레버 = 프론티어를 *바깥*으로 민다.** 두 지표가 같이 오른다. 예: 데이터 품질(중복 제거·desc 변별력·코퍼스 정제), 더 나은 알고리즘(임베딩 검색), feature 추가. **오답의 원인 자체를 없애는 것.**
- 🔴 **판별법**: 여러 시도가 전부 파레토 프론티어 위에 있으면(서로 지배 못 함) = 다이얼만 돌린 것 = 곡선을 못 밀었다. F1 상한이 안 올라간다. **곡선을 밀려면 반드시 데이터/알고리즘(곡선 레버)를 건드려야 한다.**

### 3. 파레토 지배 판정 (accept/reject 기계적 규칙)
후보 B가 baseline A를 **지배(dominate)**한다 = B가 두 지표 다 A 이상이고 최소 하나는 초과. 지배하면 무조건 채택.
- 둘 다 개선(R↑ ∧ P↑) = **곡선 바깥이동 = 진짜 개선.** 채택.
- 한쪽↑ 한쪽↓ = **곡선 위 이동 = 트레이드오프.** 지배 아님 → **목표 함수로 판정**(아래 §목표 선택).
- 둘 다 악화 = 폐기.

## 절차

### 0. 지표쌍·목표함수 먼저 확정 (측정 전)
- 상충 지표 2개를 명명(R/P, 민감도/특이도 등).
- **목표 함수를 미리 고른다**(사후 선택 = Goodhart):
  - **F1**(조화평균) = 균형. 둘 다 중요할 때 기본.
  - **Fβ** = 한쪽 가중. 감사·의료처럼 **놓치면 치명(recall 우선)**이면 F2(β=2), **오탐이 비쌈(precision 우선)**이면 F0.5.
  - **제약형** = "P ≥ 0.9 유지하며 R 최대" 식. 한 지표에 하한선이 있을 때(감사 규정 등).
- 🔴 목표는 도메인이 정한다. 감사 적발누락은 오탐보다 대개 비싸다 → recall 가중. 결정 주체는 사용자(떠넘기지 말고 추천 1개 + 이유 제시).

### 1. baseline 고정 + 측정 노이즈 제거
- 평가셋 **고정·은닉**(개선 중 수정 금지 — skill-design-standard 실험 불변식 1).
- LLM 판정이 끼면 **비결정적** → 케이스당 N회(3회+) 다수결로 재는 자를 정밀화. 단일 실행 ±몇%p는 노이즈. (지표를 바꾸는 게 아니라 측정 분산을 줄이는 것.)

### 2. 한 번에 레버 하나 (인과 분리 — 실험 불변식 3)
- 변경 1개 → 재측정 → 지표쌍 기록. 프롬프트+데이터를 같이 바꾸면 어느 게 곡선을 밀었는지 못 가른다.
- 각 시도를 (R, P) 점으로 표에 적립.

### 3. 파레토 판정 + 다음 레버 선택
- baseline 대비 지배 판정(§개념3). 지배하면 채택.
- 트레이드오프(프론티어 위)만 나오면 = **다이얼을 다 돌렸다**. F1 상한을 올리려면 **곡선 레버(데이터)로 전환**. 프롬프트를 더 만지지 말 것.
- 곡선 레버 우선순위: ① **중복/모호 제거**(가장 큰 레버 — 오답 원인 자체 소멸) ② 변별 신호 강화(desc 경계절·feature) ③ 알고리즘 교체.

### 4. 곡선 레버의 한계 인정 (과최적화 방지)
- 데이터 레버도 천장이 있다. 실측: 메타적/문맥의존 항목은 "배경 언급 vs 진짜 요청"이 **문구로 안 갈린다** → 경계절로 조이면 오탐(P)은 줄지만 정탐(R)까지 죽어 F1 하락. (라우팅 벤치 round6 실패.)
- 신호: 한 레버가 한쪽 지표를 올리며 **다른 쪽을 같은 폭으로 떨어뜨리면** = 그 항목은 이 레버의 사정거리 밖. 억지로 더 조이지 말고 **천장으로 인정**하고 멈춘다(더 짜면 과적합).

### 5. 결과 보고 형식 (운영자 선호)
- 시도별 (지표1, 지표2, 목표함수) 표 + Δ + 지배/트레이드오프 라벨.
- **F1 동률인데 R만 올랐다 = "본전"이 아니라 "recall 목표 달성 + 파레토 곡선 유지"** — 이 구분을 명확히.
- "됐냐"에 대한 정직한 답: "이 레버로 도달 가능한 최적점에 도달했고 그 천장 위치도 실측했다" ≠ "무한정 올렸다".

## 감사(audit)·임계값 튜닝 특화 노트

감사 로직·이상탐지 컷오프는 파레토 문제의 전형:
- 컷오프를 **낮추면**(더 많이 플래그) 민감도↑(적발누락↓) / 특이도↓(오탐↑) — 다이얼.
- 컷오프를 **안 만지고** 규칙 정제·feature 추가로 **둘 다 개선** — 곡선.
- 🔴 감사는 대개 **적발누락이 오탐보다 비싸다**(놓친 부정 > 헛수고) → 목표를 F2/recall 가중으로. 단 오탐이 감사 피로·신뢰 훼손을 부르면 precision 하한 제약을 건다.
- AKM/지식관리 점수 최적화도 동일: 커버리지(넣을수록↑) ↔ 신호밀도(노이즈 넣으면↓). 중복 제거가 유일하게 둘 다 올리는 곡선 레버.

## 🔴 레버는 상호작용한다 — 개별 이득을 합산하지 말 것 (2026-07-25 실측)

§2의 "한 번에 레버 하나"는 **인과 분리**를 위한 규율이지, "각각 재서 더하면 조합 성능이 나온다"는 뜻이 **아니다**. 레버 A가 +0.22, 레버 B가 +0.08이라고 A+B가 +0.30이 되지 않는다. **부호까지 뒤집힐 수 있다.**

실측(리트리벌 계층 라우팅, `scripts/retrieval_eval/FINDINGS.md`):
- 레버A = LLM 재정렬. **좁은 후보 풀**(token 라우터) 위에서 @1 **+0.22**.
- 레버B = LLM 라우터. 라우팅 실패 12→8로 회수 @10 **+0.08**.
- **A+B 조합** = 콜 429개(최대 비용)를 태우고 **세 지표 전부 다른 구성에 패배** → 파레토 지배당함, 폐기.
- 원인: B가 후보 풀을 넓히자 "의미상 그럴듯한 경쟁 문서"가 유입되고, A(스니펫만 보는 재정렬)가 그 풀에서 **렉시컬이 정확히 맞힌 1위를 밀어냈다.** 같은 레버가 좁은 풀에서 +0.22, 넓은 풀에서 -0.06.

⇒ **판정 규칙**:
1. 조합 구성을 채택하려면 **조합 자체를 측정**한다. 개별 측정값 합산으로 예측하고 넘어가지 않는다.
2. 레버 효과를 기록할 때는 **효과 크기만 쓰지 말고 그게 성립하는 전제(문맥)를 같이 적는다** — "재정렬 +0.22" ❌ / "재정렬 +0.22 (단 후보 풀이 좁고 렉시컬 정밀도가 높을 때)" ✅.
3. **후보를 넓히는 레버는 랭킹을 악화시키는 방향으로 결합**되는 경향이 있다(회수↑ ⇒ 경쟁↑ ⇒ 정밀도↓). 회수계 레버와 정밀도계 레버를 동시에 켜면 상쇄를 의심하고 반드시 실측.
4. 조합이 개별보다 나쁘면 그건 버그가 아니라 **정보다.** 어느 전제가 깨졌는지 기록하고(위 2번) 조합을 폐기한다.

실측 근거(레포 HEAD, `experimental/harbor_meta_harness/controller.py`):
```python
AGGREGATORS = {"mean": ..., "min": ..., "fraction_solved": ...}
#  전부 Sequence[float] -> float. 다목적 집계자 없음.
```
- `update_frontier()`(meta_harness.py:373)는 이름만 frontier — **task별 best
  pass_rate + 전체 best avg 기록판**이다. 지배(dominance) 판정이 없으므로
  파레토 프론티어가 아니라 **단일 지표 최댓값 갱신**이다.
- `ONBOARDING.md:63`은 "secondary metrics: latency, context cost, API spend,

### 왜 이게 치명적인가 (이 스킬의 개념2로 읽으면)

하네스 진화는 본질적으로 **곡선 레버**(스캐폴드·메모리·컨텍스트 구조를 바꿈)를
자동 탐색하는 것이다. 그런데 판정이 pass_rate 단일 스칼라면:
- 토큰·지연·API 비용을 **무한정 태워서** pass_rate를 올리는 변이가 항상 이긴다.
- 즉 탐색이 **비용축을 따라 파레토 열등 방향으로 질주**해도 게이트가 못 잡는다.
- 종속변수가 여럿인데 하나로 뭉개면, 나머지 축의 악화는 측정되지 않는다.

### 적용 규칙 (하네스 자동탐색에 이 스킬을 얹을 때)

1. **목적을 벡터로 선언한다.** 최소 (성능, 비용) 2축. 비용축은 토큰/지연/콜수 중
   도메인이 정하는 것 하나 이상. 측정 **전에** 고정(§0).
2. **채택 조건 = 파레토 지배**(§개념3). 성능만 오르고 비용이 악화된 변이는
   자동 채택하지 않고 **트레이드오프로 라벨**해 사람 판단에 올린다.
3. **"매 이터레이션 변이 강제"를 끈다.** baseline이 프런티어를 지배당하지 않으면
   `no-change`가 정당한 산출이다. 강제 변이는 Goodhart를 구조화한다.
4. **탐색 예산 자체가 비용축이다.** `eval_budget`을 쓰는 것은 좋으나, 그건
   탐색 비용이지 **산출 하네스의 운영 비용이 아니다.** 둘을 분리해 기록한다.
5. 변이 효과를 기록할 때 §"레버는 상호작용한다" 2번 규칙 적용 — 효과크기만
   쓰지 말고 성립 전제(어떤 task 분포·어떤 풀 크기에서)를 같이 적는다.

## 문헌 지위 (2026-08-03, 6소스 정독 — probe-graph-public 결정 15)

- **front-as-parent 규칙은 harness 자기개선 계층에 없다** (전 도메인 주장 아님 — 좁힌 문구가 정본).
  타 계층엔 실증 존재: GEPA(프롬프트 계층), **MOT-SR**(arXiv 2607.29561, 수식발견 —
  front→SyntaxDiv 다양성 softmax 부모샘플링. 단 그 규칙 자체 ablation 없음·통계검정 전무).
- **TRACE-Router**(arXiv 2607.22465)의 이식 규칙 2건: ① 귀속 처방 = "결정 입자를 감독
  단위까지 굵게"(콜 단위 결정 ↔ 태스크 단위 보상 mismatch가 귀속을 깬다), ② 🔴 **front 점유
  주장의 함정** — "무작위 혼합도 기대값상 끝점 사이 선분을 그린다" → front 위에 있다는 것만으론
  부족, 무작위/혼합 대조군 대비로 말해야 한다.
- 보조: BM25-at-scale(2607.26497) — 스케일 의존 교차, 단순 lexical이 front 저비용 끝 앵커.
  Safety-Gated Control(2607.27849) — 조건사다리(C0~C3)·regime map(이기는 영역과 지는 영역을
  둘 다 보고)·게이트 개입 전수 감사 문법.


- 🔴 **F1 하나만 보고 판정 금지.** F1 동률이어도 R↑/P↓면 도메인 목표가 recall이면 개선, precision이면 개악. 지표쌍을 항상 같이 본다.
- 🔴 **사후 목표 선택 = Goodhart.** "R이 올랐으니 recall이 목표였다"는 자기합리화. 목표는 측정 *전에* 도메인 근거로 고정.
- 🔴 **다이얼을 곡선으로 착각.** 프롬프트/threshold를 아무리 돌려도 F1 상한이 안 오르면 곡선을 못 민 것. 데이터로 전환하라는 신호.
- 측정 노이즈를 개선으로 오독. 다수결 없이 단일 실행 차이(±3%p)로 채택 판단하면 노이즈에 속는다.
- 곡선 레버 과신. 데이터도 천장 있음(§4). 문맥의존 항목은 desc로 안 잡힌다.
