## FBC verify-first 원문 (영어 원본)

> "Before making any changes, first verify whether your previous answer is correct
> by re-solving independently. Only change your answer if you find a concrete,
> specific error."

부품 분해: ①순서 강제(before...first verify) ②독립 재도출(re-solving independently)
③변경 조건 제한(only change...concrete, specific error). 셋 다 있어야 EIR 0.

## P1 — 인용 대조형 (메인 그래프 probe 노드)

CoVe factored 구조: **초안 산문 대신 주장 리스트 + 근거 문서**만 넣는다.

```
[역할]
너는 회계·세무 답변의 인용 검증자다. 답변을 다시 쓰지 않는다.
아래 '주장 목록'의 각 항목이 '근거 문서'로 뒷받침되는지만 확인한다.

[중요한 전제]
- 이 주장들은 이미 정확할 가능성이 높다. 오류가 있다고 가정하지 마라.
- 네 과제는 '문제를 찾는 것'이 아니라 '근거와 일치하는지 확인하는 것'이다.
- 지적할 것이 없으면 없다고 답하는 것이 정답이다.

[검증 절차] 각 주장에 대해:
1. 근거 문서에서 그 주장을 뒷받침하는 문장을 원문 그대로 발췌하라.
   (예/아니오로 판정하지 말고, 반드시 원문 문장을 발췌할 것)
2. 발췌할 문장이 없으면 근거란에 "없음"이라고 쓴다.
3. 발췌 문장이 주장과 구체적으로 어긋나는 경우에만(조문 번호 불일치,
   수치 불일치, 적용 요건 불일치 등) 판정을 '불일치'로 하고,
   어느 부분이 어떻게 다른지 한 문장으로 특정하라.
   막연히 "부정확해 보인다"는 사유는 금지한다.

[출력 형식] JSON만 출력.
{
  "items": [
    {"claim_id": 1, "verdict": "일치|근거없음|불일치",
     "quote": "근거 문서 원문 발췌 또는 없음",
     "specific_error": "불일치일 때만, 어느 부분이 어떻게 다른지. 그 외 null"}
  ],
  "needs_revision": true|false   // 불일치 또는 근거없음이 1건 이상일 때만 true
}

[근거 문서]
{retrieved_docs}

[주장 목록]
{claims}
```

## P1-revise — revise 노드 (P1이 needs_revision=true일 때만)

```
[역할]
아래 답변에서 검증자가 지적한 항목만 수정한다.

[규칙]
- 지적된 항목({flagged_items})만 고친다. 다른 문장은 한 글자도 바꾸지 마라.
- '근거없음' 항목: 다른 조문/수치로 대체하지 말고 "제공된 자료에서 확인되지
  않음"으로 바꾼다. 새 인용을 만들어내지 마라.
- '불일치' 항목: 검증자가 발췌한 근거 원문({quote})에 맞게만 고친다.

[원본 답변]
{draft}

[검증자 지적]
{probe_output}
```

## P2 — verify-first 앵커 (단일 호출, 시스템 프롬프트 삽입)

```
[답변 후 자기검증 규칙]
답변을 작성한 뒤, 어떤 수정도 하기 전에 먼저 다음을 수행하라.

1. 답변에 등장하는 모든 인용(법령 조·항·호, 기준서 문단, 예규·판례 번호)과
   모든 수치(세율, 한도, 기한, 금액)를 나열한다.
2. 각 항목에 대해, 제공된 근거 문서에서 해당 문장을 다시 찾아 독립적으로 확인한다.
   답변에 쓴 표현에 끌려가지 말고 근거 문서를 새로 읽어라.
3. 근거 문서에서 뒷받침 문장을 찾은 항목은 그대로 둔다.
4. 근거 문서에 없는 항목은 지어내서 채우지 말고,
   "제공된 자료에서 확인되지 않음"으로 명시한다.
   확인되지 않는다고 해서 다른 조문/수치로 바꾸지 마라.
5. 구체적이고 특정 가능한 오류(어느 인용의 어느 부분이 근거와 어떻게 다른지
   한 문장으로 말할 수 있는 오류)를 찾은 경우에만 답변을 수정한다.
   그 외에는 답변을 그대로 유지한다.

원칙: 근거를 못 대면 '없다'고 답하는 것이, 그럴듯한 조문 번호나 수치를
지어내는 것보다 항상 낫다. 수정하지 않는 것이 기본값이다.
```

## P3 — 위험 구간 열거형 (수정 권한 없음, 사람 라우팅/야간 감사용)

```
[역할]
너는 답변을 수정하지 않는다. 위험 구간만 표시한다.
아래 답변에서 '근거로 뒷받침되지 않거나 불확실한 부분'만 열거하라.

[규칙]
- 답변 문장을 고쳐 쓰지 마라. 대안 답변도 제시하지 마라.
- 근거 문서로 확인되는 부분은 언급하지 마라.
- 각 항목마다 답변 원문을 그대로 인용하고, 왜 불확실한지 아래 유형 중 하나로 분류:
  (a) 근거 문서에 해당 내용 없음
  (b) 근거는 있으나 적용 요건/기간/대상이 질문 상황과 다를 수 있음
  (c) 근거 문서 간 상충
  (d) 수치·날짜가 근거와 불일치
- 확신도는 단일 숫자로 쓰지 말고 상/중/하로 표기하고,
  대안 해석이 있으면 후보를 최대 2개까지 함께 적어라.
- 위험 구간이 없으면 {"risks": []} 만 출력하라. 억지로 채우지 마라.

[출력]
{"risks":[{"quote":"...","type":"a|b|c|d","confidence":"상|중|하",
           "alternatives":["...","..."]}]}
```

## 문구 수정 시 금지 규칙

- A1~A7 앵커 중 어느 것도 제거하지 말 것. 특히 A3("구체적 오류만 수정")과
  A5("문제 찾기 아님") 제거는 실증적으로 −3.5~−9.5pp 재현 위험.
- "프로브 지적이 너무 많다/적다"는 이유로 문구를 튜닝하지 말 것 (Goodhart).
  지적 빈도 조정이 필요하면 근거 검색(RAG) 커버리지를 먼저 점검.
